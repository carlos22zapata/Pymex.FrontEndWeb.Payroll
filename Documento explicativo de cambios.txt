Documentación de Entidades para Frontend - Módulo de Nómina (ToolTips)
Este documento detalla la utilidad de cada tabla del diagrama relacional y cómo debe representarse visualmente en la interfaz de usuario para garantizar una operación eficiente y adaptada a la lógica del sistema.

1. Maestros Generales (Catálogos)
Estas tablas alimentan los selectores y listas desplegables del sistema. Requieren pantallas de tipo CRUD (Crear, Leer, Actualizar, Eliminar) simples, generalmente compuestas por una tabla de datos (Data Grid) y un formulario modal.

Departments (Departamentos): Representa la jerarquía de la empresa. Dado que tiene una relación consigo misma (ParentDepartmentId), el frontend debe renderizar esto preferiblemente como un componente de tipo árbol (Tree View) o un selector en cascada para mostrar qué departamento depende de cuál.

Positions (Cargos): Es un catálogo plano. En la interfaz solo requiere un listado simple para definir los roles (ej. "Desarrollador Senior", "Gerente").

PayrollVariables (Catálogo de Variables): Define los "ingredientes" del cálculo (ej. Código: HEX, Nombre: Horas Extras). El frontend debe permitir al usuario crear estas variables para que luego estén disponibles en los selectores del sistema.

PayrollConcepts (Catálogo de Conceptos): El núcleo matemático. La pantalla debe ser un editor avanzado donde el operador define si es una asignación o deducción, si es gravable (IsTaxable), y escribe la fórmula.

2. Gestión de Personal y Reglas Salariales
Estas son las pantallas principales donde el operador de recursos humanos pasará la mayor parte del tiempo.

Employees (Ficha del Trabajador): Es el perfil maestro. El frontend debe mostrar un formulario extenso, preferiblemente dividido en pestañas (Datos Personales, Ubicación, Datos Corporativos). Aquí se integran los selectores para asignarle al trabajador su DepartmentId y PositionId.

Contracts (Contratos / Conjunto de Reglas): En la lógica del sistema, el contrato representa el conjunto general de reglas aplicables al empleado. Visualmente, esta pantalla puede vivir dentro del perfil del empleado (como un historial laboral gracias al EmployeeId). Aquí se define el sueldo base específico de ese contrato y se controla si está activo (IsActive).

ContractConcepts (Conceptos Aplicados al Contrato): En el frontend, no necesitas una pantalla separada para esto. Se debe diseñar como un componente de lista de selección múltiple (Transfer List o Checkboxes) dentro de la vista del Contract, permitiendo al operador marcar rápidamente qué conceptos (sueldo, vacaciones, utilidades) le aplican a ese contrato.

ContractVariables (Variables Fijas del Contrato): Se debe visualizar como una tabla editable dentro del perfil del contrato. Permite asignar valores constantes a las variables predefinidas (ej. si el contrato tiene un bono de alimentación fijo, se selecciona la variable y se le coloca el Value).

3. Movimientos Transaccionales (El Día a Día)
Esta sección es crucial para la usabilidad quincenal o semanal.

PayrollNovelties (Novedades del Período): Es la pantalla transaccional por excelencia. El equipo de frontend debe diseñar esto como una cuadrícula tipo Excel (Data Grid editable de alta velocidad). El operador seleccionará un período (ej. 2026-06-Q1) y el sistema mostrará una lista donde se asocian las variaciones dinámicas (como horas extras, bonos de productividad o días de inasistencia) directamente al ContractId usando el PayrollVariableId correspondiente, inyectando el valor exacto del período para el cálculo final.
